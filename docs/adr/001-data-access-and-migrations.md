# ADR 001: Data access and schema migrations

Date: 2026-08-26
Status: Accepted

## Context

The backend is moving from the stateless prototype (no database, agent output
parsed from markdown, `use_mock_data` defaults) to a Postgres system of record
defined in [`docs/schema.sql`](../schema.sql). The backend today has zero
database dependencies, so both the data-access layer and the migration tool
are greenfield choices. They are one decision wearing two hats: the migration
tool should guard whichever boundary can actually drift, and that depends on
whether a Python description of the tables (models) exists.

Forces that shaped the decision:

- **The workload is transactional.** The hardest backend component is the
  `pending_actions` executor: flip status to `executing`, call a provider,
  write the reservation, update the plan item, atomically or not at all, and
  safely retryable via `idempotency_key`. The event spine (`agent_events` to
  `agent_runs`) has the same shape. This is unit-of-work territory, not CRUD.
- **The schema evolves every phase.** Phases 1 to 6 of the frontend plan each
  touch tables. Schema changes need to surface every broken usage statically,
  because this is a solo project with no reviewer; the type checker is the
  second pair of eyes.
- **The hand-authored DDL is load-bearing.** `schema.sql` carries native
  enums, CHECK constraints (a `confirmed` reservation must have a
  `confirmation_code`, a rejected option must carry `rejection_reason`), and
  a partial unique index (one selected option per item). These constructs are
  exactly what ORM autogeneration handles worst, so they must stay
  hand-written wherever they live.
- **One source of truth per shape.** The project's standing rule (see the
  frontend plan): duplicate descriptions are acceptable only when generated
  or drift-checked against their upstream.
- **Boring conventions win.** Same principle already applied to the frontend
  stack and folder layout: prefer the most documented, most assumed path.

## Decision

**SQLAlchemy 2.0 (async) for data access, Alembic for migrations**, with the
following disciplines:

1. **Initial migration is hand-written SQL.** The first Alembic revision
   applies the DDL from `docs/schema.sql` essentially verbatim via
   `op.execute()`. It is not autogenerated, because the schema's value is in
   the constraint constructs autogenerate fumbles.
2. **Autogenerate is allowed for routine changes, always reviewed.** Column
   adds and similar mundane deltas may use `alembic revision
   --autogenerate`; constraint-bearing changes are written by hand. Every
   generated script is reviewed before it is applied.
3. **Models for transactional writes, SQL for shaped reads.** ORM models
   (2.0 typed style, `Mapped[...]`) cover entities with lifecycle and
   transactions: `trips`, `plans`, `plan_items`, `plan_item_options`,
   `pending_actions`, `reservations`, `agent_events`, `agent_runs`,
   `notifications`, identity tables. Read-heavy assembled views such as
   `GET /trips/{id}/today` may drop to Core or textual SQL and map straight
   into Pydantic response models.
4. **Eager loading is explicit, never lazy.** `selectinload` (or equivalent)
   on every relationship traversal; async SQLAlchemy raises on implicit lazy
   loads, and that error stays an error. N plus one problems fail loudly.
5. **Schema truth and drift checks.** Once the initial migration lands,
   `backend/migrations/` is the operational truth for schema state.
   `docs/schema.sql` remains the readable reference and is kept honest by a
   CI job that runs migrations against a scratch Postgres, dumps
   `pg_dump --schema-only`, and diffs it against `docs/schema.sql`
   (normalized). Model-to-database drift is guarded by `alembic check` (or
   an equivalent empty-autogenerate assertion) in the same CI job. This
   mirrors the frontend's generated-client sync check against
   `docs/openapi.yaml`.
6. **Pydantic stays separate from the models.** API schemas (contract) and
   SQLAlchemy models (storage) are distinct layers mapped explicitly
   (`model_validate(..., from_attributes=True)`). The contract is
   deliberately not the table shape (derived fields like `needs_you_count`,
   assembled views, hidden internals), and the prototype's `emoji_badges`
   is the recorded counterexample of what merging the layers produces.

## Alternatives considered

### dbmate + asyncpg (pure SQL stack)

Migrations are plain `.sql` files; data access is the raw driver. Genuine
strengths: one language end to end, radical simplicity, and dbmate re-dumps a
canonical schema file after every migration, which solves the
`schema.sql`-versus-migrations drift natively. Rejected because it leaves the
other boundary unguarded: with no model layer there is nothing to diff the
Python code against, so every query is validated only at runtime against a
live database. The transactional workload would also require hand-building
session and transaction management around every executor flow. The drift
risk does not disappear under this stack; it relocates from
"schema file versus migrations" (which dbmate solves) to "Python code versus
database" (which nothing in this stack solves). For this workload the second
boundary is the dangerous one. dbmate would be the right choice for a small,
stable, read-mostly schema with thin CRUD endpoints.

### SQLModel

One class serving as both Pydantic schema and SQLAlchemy table. Rejected
because it merges the two layers this project deliberately keeps apart
(decision point 6), lags SQLAlchemy releases, and is effectively a thin
layer with a narrow maintainer base. Its benefit is largest when the API
mirrors the tables, which this API intentionally does not.

### Tortoise ORM / Piccolo

Async ORMs with their own migration tools (Aerich, Piccolo migrations).
Rejected on ecosystem size: the migration tooling is the weak link, and both
are roads less traveled compared to the SQLAlchemy plus Alembic pairing that
FastAPI documentation and the wider ecosystem assume.

### Django ORM

Excellent ORM and migrations, but it brings Django; wrong fit for the
existing FastAPI backend.

## Consequences

- New backend dependencies: `sqlalchemy[asyncio]`, `alembic`, `asyncpg` (as
  SQLAlchemy's async driver), plus a test-time Postgres (Testcontainers or
  compose service) for integration tests and the CI drift job.
- The walking-skeleton work order becomes: Alembic init, hand-written initial
  migration from `docs/schema.sql`, models for the skeleton tables, session
  wiring in FastAPI, seed script, then the auth and trips read endpoints.
- `docs/schema.sql` gets a header note pointing to `backend/migrations/` as
  operational truth and to the CI check that keeps the two in sync.
- Contributors (and future us) must learn the async SQLAlchemy session
  patterns; the mixed discipline in decision points 3 and 4 is the guardrail
  against the classic ORM failure modes.
- If the CI drift checks are ever skipped or removed, decision point 5's
  guarantees lapse silently; treat those jobs as load-bearing, not optional.
